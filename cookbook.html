OType cookbook

Short recipes, one need each: copy one into a .OTY file of /SCRIPTS on the card, or start from it. Every recipe below is checked by the test suite (tools/test_otype_run.py, CookbookRecipes): it passes the checker with the unit's profile and runs in the simulator. Firmware authors: the last part, "Integrating the engine", is for you. The language itself is in docs/syntax.md; every operation, with its arguments, is in the command reference (docs/cheatsheet.html).

Try any recipe on the computer before the card:

python3 tools/otype.py check --profile m1 MY.OTY
python3 tools/otype.py run four_floor MY.OTY --seed 1
python3 tools/otype.py run four_floor MY.OTY --seed 1 --bank PATH/TO/bank01.work --pattern 1   # your own pattern, read only

Conventions used here: a function acts on the current track and the current pattern unless it says trk …; steps are numbered from 1; i is the step (or loop index) being visited.

1. The smallest script: four on the floor

  • menu "CATEGORY" >> "NAME" puts the function in the script menu of your firmware, under its category.
  • confirm asks YES/NO first, with your own question; use it on anything that removes something.
  • l 1 16: loops i from 1 to 16; if … : runs the rest of the line when the condition is not 0.

2. Parameters the player sets before running

param NAME default min max declares a value the player sets before the run, between min and max; the firmware's menu shows it. steps all: + each: visits every step; er.r k n r s is 1 when step s plays in a euclidean rhythm of k hits over n steps rotated by r.

3. Typed parameters: yes/no, a choice, a folder

  • bool shows YES/NO (1/0); option shows labels, the script reads their index from 0.
  • prob p: runs the rest of the line p percent of the time.
  • a…z (except i) are variables; a 1 sets a, sub i 1 is i - 1 (prefix notation).

4. Random, but the same every time: seeds

Without seed, each press draws new numbers. With seed n, a press always gives the same result; the simulator and the unit agree on it, so run --seed shows exactly what the machine will do.

5. Several tracks in one press, with your own functions

def name | args declares a function that takes arguments; call it with name | values. A function without menu is not shown in the menu: it is a brick for the others. trk t: acts on track t for the rest of its block.

6. A page of six encoders

page "LABEL" puts the function on a page of encoders instead of the menu (when your firmware has one: the engine itself only lists menu functions); its parameters (at most six) are the encoders A..F. The page reruns it each time an encoder moves, on the pattern as you left it, and keeps the result as a layer you print or discard. A page function takes no argument and does not touch the card, the Static slots.

7. Accents with velocity curves and p-locks

dr.v c s is a velocity 0..127 from one of eight 16-step curves. pl.set s p v locks parameter p (here amp.vol) on step s; a step without a trig is skipped and counted, never turned into a trig. Parameter names: amp.vol, lfo.spd 1…, or by page and position: fx1 1 is the first FX1 parameter.

8. Humanize: micro timing and gentle volume

micro.rnd x shifts each trig by up to x micro steps either side. pl.vary p x moves existing locks of p by up to x percent; steps without that lock are left alone. Both already visit every step with a trig: wrapping them in steps has.trig: each: would run them once per trig and cost sixteen times more (the checker refuses it: over 4096).

9. Trig conditions: a fill on the last bar

cond.set s c writes the trig condition: fill, !fill, pre, nei, 1st, a ratio a:b, or a probability among the Octatrack's own (25%, 50%…). off removes it.

10. One press a variation, the next press back: state between presses

flip alternates 0, 1, 0… on each read and keeps its value between presses (so do o and drunk). ? c x y is x when c is not 0, else y: odd presses use seed 7, even presses seed 0. steps has.trig: restricts the next lines to the steps that hold a trig.

11. Fill the Static slots from a folder the player picks

dir path [deep] lists the files of a folder of the current set (deep: with its subfolders); ext and match filter that list. The loop gives every free Static slot a random file of the list, never the same one twice (file.pick); it stops when the files or the free slots run out. static.load n f loads file f of the list into Static slot n; static.firstfree is the first free one (0 if none). Lists hold up to 4096 names. The Static list is the sample list of the project: the Flex list is separate. More ways to fill, clear and randomize the slots are in recipe 33.

12. A kit from a folder, locked at random on the trigs

file.pick never gives the same file twice in a row of picks; slots.clr / slots.add build a working set of slots, slots.rnd draws one of them. break leaves the loop (no free slot, or no file left).

13. A walk through samples: drunk

drunk moves by -1, 0 or +1 on each read, between drunk.min and drunk.max: neighbouring trigs get neighbouring sample slots.

14. Drum and bass on eight tracks

A whole drum and bass tune, played live on the eight tracks from eight Static slots, never twice the same. It is the showcase of the 1.1 live scripts: launch 384 waits for the bar, in clock 24 runs every sixteenth, four vars keep the step, the bar and two filters from one sixteenth to the next.

  • Set it up once. [DNBFILL.OTY](../modules/otype/examples/DNBFILL.OTY) (POOL >> DNB FILL) fills them from a folder. Slots 1..8 hold the kick, snare, ghost, hats, ride, break, a reese bass and an fx; tracks 1..8 are Static machines on slots 1..8, with the stock filter in FX1 and its BASE at 0. Start on an empty pattern: the script plays its own hits, it does not touch the pattern's trigs.
  • The arrangement, 32 bars. b is the bar in the arrangement. Bars 1..12 are the groove; 13..16 a breakdown where only the break plays, half time, its filter opening a step each bar; 17..32 the drop, with a fill at the end of every fourth bar. Then it starts again.
  • The groove. a is the sixteenth in the bar: the two-step (kick on 0 and 10, snare on 4 and 12), a pushed kick on 7 one time in five, random ghosts, hats with a new volume on every sixteenth, the ride on the off-beats, the reese on the "and" of 2 and 4 with a pickup on 11.
  • The filters. reese is a random walk: each bar the reese's filter WIDTH moves by up to 12, between 30 and 120. rise opens the break over the breakdown; the drop puts it back wide open.
  • The file is [modules/otype/examples/DNB.OTY](../modules/otype/examples/DNB.OTY).

15. A fill on the bar

A live script that changes the pattern on the bar, hands-free: launch 384 makes its first run land on the next bar, then in clock 384 runs once per bar. Track 8 is the fill track: every fourth bar, four trigs appear at the end; on the other bars they are removed. The rest of the pattern keeps playing.

l 13 16: writes steps 13..16. Use a track whose steps 13..16 are free, or a throwaway pattern: tr.del removes whatever was there. The same idea works on any track and any steps.

16. A fill where the snare drops out

in trig 4 all: wakes on every trig placed on track 4, even when it does not play: a condition that failed, or a muted track. trig.hit says which. When the snare is refused, a percussion fill takes its place on track 8.

The wake is dated on track 4's tick, so the fill lands exactly where the snare would have. Put a fill sample in slot 8 and assign it to track 8; play 8 plays it. To put the fill on the snare track itself, play 4.

17. Live sequencing module

in clock N: registers a live sequencer module executed every N ticks (24 ticks = 1 quarter note). On each clock tick, the module can query sequencer status (seq.run, seq.step t, seq.mute t), prepare per-hit locks for the next hit with nx.smp n (Static sample slot 1..128) and nx.pl p v (parameter p in 0..29, clamped by the part's descriptor like pl.set), and schedule track playback with play t (which consumes and resets the nx.* locks). In v1, the first trigger right after PLAY may be delayed by up to one timer period (~10 ms); all subsequent triggers fall on the step grid. While a menu script is running or awaiting user input (ask, confirm), modules are silent; their deadlines are skipped and counted, and they resume on the grid afterwards.

18. Pads from a MIDI controller

A controller on MIDI channel 1 plays tracks 1..8 from notes 60..67, at the note's velocity: note 60 plays track 1, note 67 track 8.

in note 1: wakes on each note; a is the track; trk.level makes the track as loud as the note. note.vel is the velocity of the note that woke the block; midi.vel 1 keeps the same number after the block, and midi.note 1 the note. Track level is 0..127, the same range as the velocity, so the number is used as it comes. Notes outside 60..67 are ignored: the if keeps play in range.

19. A filter and a density knob from two CCs

Two knobs on another box shape a live line: CC 74 on channel 1 sets FX1's first parameter (the filter cutoff on a default part), CC 71 sets how often the track plays.

param … cc ch n binds a parameter to a controller and the engine keeps it up to date; in cc ch n: reads a controller value in the script. The filter is written to the part (par.set), not locked on a step, so it affects the whole track; the density is a var set by the CC and read by prob. The parameter page shows the binding (CUT 64 CC74) but does not refresh when the CC moves: the value the script reads is current. On a part where FX1 is not a filter, fx1 1 is still the first parameter of FX1.

20. Mirror an external controller

midi.cc ch n, midi.note ch and midi.vel ch read what the last MIDI message received on a channel left behind, so a knob on another box can drive a p-lock: CC CUT locks the first trig's volume to the knob's current value. n2trk plays the track the last note names. send.nrpn ch p v is the output side: one NRPN as its four Control Changes, all four or none if the transmit buffer is short.

21. A generative line for an external synth

in clock 24: runs every sixteenth; each run sends a note to channel 5 with 60 % probability, walking up a twelve-note ladder, and a filter CC every two beats. The external synth makes the sound; the Octatrack is the sequencer.

send.note ch n vel dur schedules the note-off dur ticks later (24 = one sixteenth here). A note already playing on the same channel and note number is cut before the new one. send.cc and send.prog are the other two; send.nrpn sends a whole NRPN as its four CCs. Nothing is sent when the transmit buffer is full: the script never blocks.

22. Record a loop on the trigs

Places a recorder trig on step 1 of the track in context, listening to input A (INAB = 2 on track 1) for four steps (RLEN 4): at 120 BPM the recorder writes exactly 22 050 samples and stops. rt.add s src with the mask 1 (AB), 2 (CD), 4 (internal) and 7 for all three, as the stock trig does; rt.del s removes the recorder trig of a step (its sources, one-shot flag and micro-timing) and rt.clr removes them all. rec.src t n v and rec.len t v are the RECORDING SETUP values of a track, stored in the part like the page's own knobs.

23. One take, then the next script arms it again

ro.add s [src] is a recorder trig with the one-shot state: it records once, and the next time the pattern reaches the step it stays silent, as a one-shot sample trig does. rec.trig t v picks ONE (0), ONE-2 (1) or HOLD (2) and rec.loop t v whether the take loops when played back. To take another one, re-arm with os.arm (all one-shot trigs of the track) — that is what [STOP]+[STOP] does for the whole pattern. rec.arm t [src] starts a recording without waiting for a trig: it is the panel's [TRACK]+[AUDIO REC], QREC included.

24. Resample the loop

The recording can start from a script, not from a key: rec.arm t [src] is [TRACK]+[AUDIO REC]. rec.src picks where the track's recorder listens, rec.len how much it takes. Here the bar is captured from MAIN every time track 1's first step plays; the second function arms on any note on channel 1.

  • rec.src 1 3 9: source 3 of track 1 is SRC3, set to MAIN. rec.len 1 16 is one bar of 16 steps; rec.arm 1 4 starts it from SRC3 only. The source mask adds 1 (AB), 2 (CD) and 4 (SRC3).
  • QREC still applies: with a quantisation set in RECORDING SETUP, the take starts on the next quantum, not on the tick that armed it. The recorder runs for RLEN, so the buffer always holds the last bar captured; save that take as a WAV with recipe 26 (src.save) and load the WAV into a Flex slot to play it back.
  • The take overwrites the track's recorder buffer: use a track whose recorder you are not using, and a project you can reload.

25. An acid line, wired

Two live scripts, wired by name. acid runs every sixteenth, sends a gate on output 1 every quarter note and publishes a cutoff value on its output 1. follow wakes on that gate, reads the value with cv acid 1 and sets FX1's cutoff on track 2 before it plays: a 303 line where the filter follows the master.

cv acid 1 is 0 when acid is not running: the follower then plays with the base value, 40. The cascade is same-tick: follow's play 2 lands on the master's tick. gate and out only exist in live scripts; a name in in gate / cv is the function's name, up to 8 characters.

26. Save an audio take and load it into a Flex slot

input sample declares that the function operates on the active audio sample context (recording buffer or audio editor). src.save commits the take to durable storage on the card; upon return, file.at 1 holds the newly written WAV file path. flex.load 1 file.at 1 assigns the new recording to Flex slot 1.

Clearing all Flex slots is the same loop as for Static:

flex.firstfree is the number of the first free Flex slot (0 if all 128 are used), the Flex twin of static.firstfree. flex.del n empties Flex slot n and gives its memory back, the Flex twin of static.clr; an empty slot is left alone. Like flex.load over a used slot, it is refused with STOP FIRST while the sequencer plays. The eight recorder buffers are not Flex slots: flex.firstfree never counts them and flex.del cannot empty them (both experimental).

27. Build a sliced sample chain from a folder

cat.clr clears the host's concatenation list (up to 64 files). cat.add appends files from the current directory list. cat.save "NAME" stitches the concatenated files into a single WAV with automatic .ot slice markers per source file, saved in the context directory or /AUDIO. Upon success, file.at 1 points to the generated chain. (Experimental. A very large folder is slow to read on the unit itself, before the first file is processed: allow time.)

28. Batch normalize samples

norm path db scans all frames of a WAV file on the card and calculates the gain needed to reach the target peak level (-12..0 dB), updating the .ot metadata in place without destructive audio rewrites. (Experimental. A very large folder is slow to read on the unit itself, before the first file is processed: allow time.)

29. An effect and an LFO, set in the part

fx.type x y picks entry y of effect slot x's list (0 = none). lfo.dest x p aims LFO x at a parameter; par.set p v writes a parameter of the current part (not a lock): the value the track plays wherever no lock says otherwise, clamped to its range. A part holds much more than this (the machines and their slots, every parameter page, the scenes); the recipe changes one effect and one LFO of the current track only. These changes survive a power cycle; RELOAD PART on the unit goes back to the saved part.

30. Scenes to play with the crossfader

scn.clr unlocks all 16 scenes; the loops put a random lock on every LFO and FX parameter (6..11 and 18..29) of scenes 2..16 (scn.set scene param value; j is the scene, i the parameter). Put scene 1 on A, any other on B, and move the crossfader. par.min p and par.max p are the bounds of parameter p on the current track, so the draw stays inside what the parameter accepts; a parameter the part disables is refused (and counted) by all three operations.

31. Show where pat.go landed

After a run the menu says DONE. msg replaces it with your own text, so you can see which pattern or bank a script chose:

The end message reads BANK 2 PAT 7 (a number, a space, the next item; the last msg of the run wins). **Show the variables you gave to pat.go, not pat.cur / bank.cur read afterwards:** when the sequencer is playing, the Octatrack queues a pattern change until the end of the current pattern (the stock call pat.go uses does that itself), so pat.cur right after pat.go can still say the old pattern, while the simulator already answers the target. The variables are right in both cases. A text is at most 29 characters in the worst case, a number counting as 6 (-32768): msg "TEMPO" tempo is fine, a long sentence is refused when the script loads.

32. Copy a pattern from a script

pat.copy a b is [FUNCTION]+[STOP] without the clipboard: pattern a lands on pattern b of the current bank, trigs, locks, length and the part assigned together, in the bank and in the pattern's SRAM copy. The stock's undo snapshot is taken first, so UNDO PATTERN can bring the old b back; a copy waiting in the pattern clipboard is left alone. It is a menu script: a live script is refused (op pat.copy not allowed in a live script), and the run stops if a is b.

33. Bulk jobs on the Static slots, scenes, LFOs and effects, as loops

OType has no one-shot helper for these: a few lines of loop do each, and you can change them. Each recipe below stands alone.

Fill the Static slots

file.at i is the i-th file of the list in its sorted order: the free slots take the files in order. A file the unit refuses leaves its slot free, and the next file is offered to it.

Fill the Static slots at random

Recipe 11: file.pick instead of file.at i.

Shuffle the Static slots

static.swap a b trades the samples of two Static slots: each is reloaded by name from the other, an empty slot takes the sample and leaves its partner empty, and a = b does nothing. The loop is a Fisher-Yates shuffle: slot i swaps with a random slot from 1 to i. It stops at the first free slot, so it shuffles the run of used slots from slot 1 (what the fill recipes leave) and leaves the rest alone. A sample the unit refuses to reload empties its slot, as static.load does.

Random LFOs

Parameters 6..11 are the speeds and depths of the three LFOs (lfo.spd n, lfo.dep n); lfo.dest x p aims LFO x at one of the effect parameters (18..29) and lfo.wave x w picks its waveform (0..6 on a stock unit). par.min p and par.max p give the bounds of parameter p, so the draw covers its whole range; par.set clamps the value to it anyway.

Random effects

fx.type x y picks entry y of effect slot x's list; 0 is NONE, so the draw starts at 1. fx.count x is the number of entries of that list, NONE included: the last entry is fx.count x minus 1, whatever the firmware (the FX2 list changes with a remixed firmware). A list that holds NONE alone makes the draw 0 or 1; 1 is out of range and counted, 0 leaves the effect off.

Limits worth knowing

  • 4096 operations per press (the checker prints each function's worst case); 4096 file names per list.
  • Up to 8 parameters per function in a menu, 6 on a page.
  • A function that fails to load is refused alone: the rest of the file loads, and /SCRIPTS/ERRORS.TXT says why, with the line.

Integrating the engine (for firmware authors)

OType is shared with other custom firmware authors as sources: build it, link it where your firmware wants it, make the stock OS enter it at one place, and give it your own interface. The full contract is firmware/README.md; these are the steps in practice.

I1. Build and link at your addresses

cd firmware
python3 build/layout.py                                        # the block you must reserve: 2,187,688 B, align 16
python3 build/build.py --base CODE_ADDRESS --region REGION_ADDRESS  # replace with your addresses

build/out/otype.bin is the code (not position-independent: link again for another address). Its exact size and SHA256 are recorded in build/out/otype.json after each link. build/out/otype.json lists what to write into the OS.

I2. Write the entry point

From your unpacked system image, check the site and write the bytes otype.json gives. The bytes are the module's own jmp, not Elektron's:

import json
d = json.load(open("build/out/otype.json"))
img = bytearray(open("system-image.bin", "rb").read())
for e in d["entry_points"]:
    off = int(e["site"], 16) - image_base
    w = bytes.fromhex(e["write"])
    # check first: the site must hold e["displaced"] (disassemble it), or the image is not the expected one
    img[off:off + len(w)] = w
open("system-image-otype.bin", "wb").write(img)

Before patching, disassemble the site with the load address and target CPU for your OS build. The instructions must match displaced in otype.json.

I3. Put the code in memory

Your boot loader copies otype.bin to the --base address after stock startup initialisation and before your interface first calls it, then pushes and invalidates the caches. Reserve this code area against stock writes throughout startup, project loading and use. Appending the binary to an image alone is insufficient. The module sets itself up on first use.

I4. Reserve the block

The block is the module's alone and may start uninitialised. The usual place is the top of the sample memory, made smaller by the same amount. To check that nothing of the stock writes there, fill the block with a pattern in an emulator, boot, load a project, play and record, and compare.

I5. Check it on the unit

  1. The unit behaves as stock until your interface calls the engine (menus, key combinations, projects).
  2. Put recipes 1 and 11 in /SCRIPTS/ on the card. LOAD through your interface: ot_nloaded counts the functions, and /SCRIPTS/ERRORS.TXT appears.
  3. Add a broken function to the file and LOAD again: only it is refused, ERRORS.TXT names its line.
  4. Run FOUR FLOOR, then power-cycle without saving: the trigs are still there, like a stock edit.

I6. Your own interface

The engine ships no interface: a key, a menu, a page or a trig of your firmware calls it. List the scripts, ask what they need, run them (assembly, UI task):

        clr.l   -(%sp)                      | cdecl, one argument (unused here)
        jsr     otype_ot_load:l             | once: read /SCRIPTS, compile, load (writes ERRORS.TXT)
        addq.l  #4,%sp
        jsr     otype_prepare:l             | index the staged table before C metadata/parameter calls
        ...                                | require d0 = 0; otherwise handle the load refusal
        ...
        move.l  #3,otr_mail+4:l             | function index in the loaded table
        move.l  #1234,otr_mail+8:l          | seed (low 16 bits)
        jsr     otype_run:l                 | runs on the current pattern and commits; d0 = 0: ok

After otype_prepare succeeds, the parameters, the confirm text and the menu paths of each function are read from the loaded table with otc_vm_fn_param, otc_vm_fn_confirm and ot_ctx (firmware/README.md, "Your own interface").

To build a menu, read each function's category and name from ot_ctx, group by category and sort as you like; input sample is a flag of the function's entry (docs/syntax.md), so a recorder view can list only the functions that act on an audio take. Ask the parameters and the confirm YES/NO before the run, then show DONE or the run's msg.
